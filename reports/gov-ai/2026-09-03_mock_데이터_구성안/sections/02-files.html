2. 몇 개로 나누는가 — 8종 + 매니페스트

나누는 축이 둘이다. 엔드포인트가 다르면 파일이 다르고, 같은 엔드포인트라도 파라미터에 따라 응답 스키마가 갈리면 또 나눈다. 그래서 호출은 다섯인데 파일은 여덟이 된다.

API 1  /reports/weekly      → 4개   format·week·refresh 세 파라미터로 스키마가 갈린다
API 2  /certificate        → 1개
API 3  /analysis/diagnose  → 1개
API 4  /reports/history    → 1개   ← 화면이 쓰는 유일한 파일
API 5  /feedback/approve   → 1개
                              ─────
                              8개  + _manifest.json (근거 보존)

API 1이 넷으로 갈리는 이유

같은 /reports/weekly/{uuid}인데 파라미터 하나에 따라 돌아오는 모양 자체가 달라진다. 어댑터가 이 셋을 모두 흡수해야 하므로 각각을 남긴다.

파일붙인 파라미터크기무엇이 들어 있나
api1-weekly-cached.json?format=json5,452기본형. 최상위 10키 — studentUuid·주차 4종·cached와 metrics(23필드)·diagnosis(10)·weakness(5)·risk(4) 네 블록. cached: true다
api1-weekly-past-W34.json&week=2026-W341,601과거 주차. 최상위 키는 같은데 metrics가 23 → 7필드로 줄어든다. 힌트·재시도·정체·에러 유형·신원이 통째로 빠진다. 결측 처리를 검증하는 유일한 재료다
api1-weekly-refresh.json&refresh=true6,104재분석본. cached: false이고 캐시본과 21개 필드의 값이 다르다. 같은 주차라도 부르는 시점에 따라 값이 흔들린다는 증거
api1-weekly.mdformat 생략4,671Markdown 응답. 종합 진단·정량 지표·근거와 취약점·권장 조치 네 절로 렌더된 문서다. JSON과 같은 내용이고 추가 필드는 없다

나머지 넷은 엔드포인트마다 하나씩

파일호출크기무엇이 들어 있나
api2-certificate.jsonGET /certificate/{uuid}3,629증명서 8블록 — student·summary·technical_proof·project_and_portfolio·ai_analysis_narrative·human_in_the_loop 등. summary.total_steps가 여기에만 있어 진도의 분모를 준다
api3-diagnose.jsonPOST /analysis/diagnose/{uuid}3,624진단 결과가 최상위 10키로 평탄화돼 온다. API 1의 diagnosis 블록과 키가 똑같은데 확신도가 0.85로 다르다 — 부를 때마다 새로 분석하기 때문이다
api4-history.jsonGET /reports/history/{uuid}12,114화면의 주 재료. W33~W36 4주가 배열로 온다. 행마다 최상위 20키 + metrics_snapshot인데, W35·W36은 23필드, W33·W34는 7필드로 축약돼 온다. 필드명이 weekly와 달라 student_uuid·recommendations·feedback_draft·risk_status로 온다
api5-approve.jsonPOST /feedback/approve387request(4필드)와 response(3필드)를 함께 담았다. 실제로는 호출하지 않았다 — 승인 로그가 누적되고 삭제 API가 없어, 관측된 형태로만 구성했다

매니페스트

파일크기무엇이 들어 있나
_manifest.json5,550수집 범위(scope)·용도(purpose)·데모 수강생 식별자(demoStudent)·파일별 호출(files)·손댄 내역(transforms)·값의 출처(provenance)·알려진 특이사항(knownQuirks). 근거를 파일 안에 남긴다

파일마다 화면의 어디에 쓰이나

여덟 중 화면에 값을 그리는 것은 둘이고, 하나는 화면의 특정 상태를 만들며, 나머지는 렌더에 직접 닿지 않는다.

파일화면 항목어떻게 쓰이나
api4-history.json거의 전부
헤더 주차 · 이번 주 나의 수준 · 지표 8칸 · 서술 4섹션 · 강사 피드백 · 생성 표기 · 주차 관리 표시		mock 핸들러가 소비하는 유일한 파일이다. 배열 4건이 주차 브라우저가 되고, 행마다 25개 필드가 화면 항목으로 흩어진다. 필드와 항목의 1:1 대응은 항목별 데이터 보고서 2장에 있다
api2-certificate.json지표 · 진행 단계의 분모summary.total_steps가 10/10 완료의 뒤 숫자다. 지금은 화면이 상수 10을 쓰고 있어 이 파일이 대기 상태이며, 연결하면 상수를 없앨 수 있다
api1-weekly-past-W34.json축약 주차 안내 문구
"이 주차는 일부 지표가 수집되지 않아 0으로 표시됩니다"		metrics 7필드 응답을 재현해 partialMetrics 경로를 검증한다. 값을 그리지는 않지만 화면의 한 상태를 만든다
api5-approve.json강사 피드백 승인 게이트
"강사·매니저가 검토 중이에요"		승인 요청·응답의 형태를 잡아둔 것이다. 지금은 화면이 마지막 주차만 미승인이라는 임시 규칙을 쓰지만, 실연동에서는 이 응답이 게이트를 여는 신호가 된다
api1-weekly-cached.json—metrics 23필드가 api4의 metrics_snapshot과 같은 모양인지 대조한다. 어긋나면 어댑터가 깨진다
api1-weekly-refresh.json—재분석하면 21개 필드 값이 바뀐다는 사실을 잠가둔다. 화면이 캐시본을 전제하고 있는지 점검할 때 쓴다
api1-weekly.md—같은 데이터의 문서 표현. JSON에 없는 항목이 여기 있지는 않다는 것을 확인해 둔 자료다
api3-diagnose.json—등급·확신도가 api4와 어긋나는지 대조한다. 실제로 확신도가 0.8과 0.85로 다르다
_manifest.json—어느 명령으로 언제 받았고 무엇을 손댔는지. 값이 달라졌을 때 원인을 가리는 근거다

api4-history.json 한 행이 화면에 흩어지는 모양

이 파일만 항목 단위로 한 번 더 편다. 나머지는 화면에 직접 닿지 않는다.

화면 항목읽는 필드성격
헤더 · 주차week_no · week_range변환 (ISO → 기수 경과 주차)
이번 주 나의 수준grade · confidence원천 + 라벨 변환
지표 8칸steps_completed · current_step · active_days_count · stalled_days_on_current_step · days_since_last_activity · error_per_run · total_errors · total_runs · hint_requests_count · hint_per_active_day · avg_retry_gap_min · max_retry_gap_min · top_error_types원천 (분모만 상수)
지난주 대비 변화steps_completed · total_runs · error_per_run계산 — 앞 행과 비교
잘하고 있는 점위 다섯 지표생성 — 조건에 걸린 것만
보완하면 좋은 점weak_patterns원천 서술 그대로
이번 주 학습 제안hint_per_active_day · avg_retry_gap_min · days_since_last_activity · stalled_days_on_current_step · error_per_run · grade생성 — 임계값에 걸린 것만
강사 피드백feedback_draft원천 + 승인 게이트
생성 표기llm_provider · llm_model원천
주차 관리 표시risk_status원천 + 판정
그래서 파일 하나가 비면 화면이 통째로 빈다. api4-history.json이 없거나 userId 키가 어긋나면 빈 배열이 돌아와 리포트가 하나도 뜨지 않는다. 나머지 일곱은 없어도 화면은 그려진다 — 대신 스키마가 바뀌었을 때 알아챌 수단이 사라진다.
