2. 몇 개로 나누는가 — 9개 + 매니페스트

호출 5개에 대해 응답 형태가 갈리는 변형을 더해 9개가 된다. API 1은 같은 엔드포인트인데 파라미터에 따라 스키마가 달라져 셋으로 나눴다.

파일호출크기무엇이 들어 있고 왜 필요한가
api1-weekly-cached.jsonGET /reports/weekly/{uuid}?format=json5,368기본형. metrics 24필드 전체. 스키마 기준이 된다
api1-weekly-past-W34.json…&week=2026-W341,601과거 주차. metrics가 7필드로 축약된다. 결측 처리를 검증하는 유일한 재료
api1-weekly-refresh.json…&refresh=true6,025재분석본. 캐시본과 21개 필드의 값이 달라진다. 같은 주차라도 호출 시점에 따라 값이 흔들린다는 증거
api1-weekly.mdGET /reports/weekly/{uuid}4,623format을 빼면 Markdown이 온다. 같은 데이터의 문서 렌더링
api2-certificate.jsonGET /certificate/{uuid}3,583total_steps가 여기에만 있다. 진도의 분모
api3-diagnose.jsonPOST /analysis/diagnose/{uuid}3,624진단 블록이 최상위로 평탄화된 형태. API 1의 diagnosis와 키가 같고 값이 다르다
api4-history.jsonGET /reports/history/{uuid}?limit=3011,948화면의 주 재료. W33~W36 4주치가 배열로 온다
api5-approve.jsonPOST /feedback/approve387요청·응답 형태. 실제로는 호출하지 않았다 — 승인 로그가 누적되고 삭제 API가 없어, 관측된 형태로만 구성했다
ext-sync-students.jsonGET /sync/students?limit=2001,108문서 밖 엔드포인트. 출결·과제·퀴즈·atmux 상세가 여기에만 있다. ext- 접두사로 명세서 밖임을 표시
_manifest.json—3,422출처·수집 시각·치환 규칙·알려진 특이사항. 근거를 파일 안에 남긴다
화면은 api4-history.json 하나만 쓴다. 그런데도 9개를 두는 이유는 나머지가 대조용이기 때문이다 — 필드명이 호출마다 다르고(studentUuid↔student_uuid), 같은 값이 호출마다 어긋나며(확신도 0.8↔0.85), 주차에 따라 필드가 사라진다. 어댑터가 이 셋을 모두 흡수하는지 검증하려면 원본이 남아 있어야 한다.
