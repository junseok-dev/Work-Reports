2. mock 7종 한눈에

폴더에는 파일이 아홉 개지만 mock으로 쓰이는 것은 JSON 7종이다. 나머지 둘은 성격이 다르다 — 하나는 참고 문서, 하나는 기록이다.

갈래개수무엇인가
mock 데이터7종index.ts가 import하는 JSON. 화면과 테스트가 실제로 읽는다
참고 문서1건api1-weekly.md. Markdown이라 import할 수 없다
기록1건_manifest.json. 데이터가 아니라 데이터의 출처다

2.1 무엇을 넣을지 — 세 가지를 다 통과해야 한다

응답이라고 다 넣지 않는다. 셋 중 하나라도 걸리면 mock에 들어가지 않는다.

기준왜 그런가여기서 걸러진 것
1명세서의 다섯 API여야 한다문서에 없는 엔드포인트는 계약이 아니다. 언제 사라져도 이상하지 않은 것에 화면을 의존시킬 수 없다/sync/students — 출결·과제·퀴즈·학습 시간이 여기 있었지만 뺐다
2import할 수 있어야 한다index.ts가 읽어 핸들러에 넘겨야 mock으로 동작한다. 형식이 다르면 화면도 테스트도 못 쓴다api1-weekly.md — 내용은 같지만 Markdown이라 참고 문서로 분류
3실제로 호출해 받은 값이어야 한다지어낸 값을 섞으면 실연동으로 바꾸는 날 무엇이 달라졌는지 가릴 수 없다채워 넣었던 W33·W34의 지표 — 되돌리고 축약된 채로 뒀다

2.2 어떻게 나눌지 — 재현 단위와 스키마

통과한 응답을 파일로 자르는 기준이다. 한 파일이 한 번의 호출로 재현되어야 하고, 어댑터가 다르게 처리해야 하는 응답은 갈라야 한다.

규칙이유적용 결과
A엔드포인트가 다르면 나눈다파일 이름이 곧 재현 명령이 된다. 어느 호출에서 온 값인지 잃지 않는다5개 호출 → 최소 5개 파일
B스키마가 갈리면 또 나눈다키가 달라지면 어댑터가 다르게 처리해야 한다. 둘 다 흡수하는지 확인하려면 원본 두 벌이 필요하다API 1이 ?format=json · &week= · &refresh=true로 세 벌
C값만 다르면 나누지 않는다같은 모양을 여러 벌 두면 어느 것이 기준인지 흐려진다주차별 파일을 따로 두지 않았다
 
API 1  /reports/weekly      → JSON 3종   B에 걸려 셋으로
                                 + Markdown 1건 (기준 2에 걸려 참고 문서)
API 2  /certificate        → 1종
API 3  /analysis/diagnose  → 1종
API 4  /reports/history    → 1종    ← 화면이 쓰는 유일한 파일
API 5  /feedback/approve   → 1종
                             ──────
                             JSON 7종

나누지 않은 것들 — 규칙 C가 걸러낸 경우

나눌 뻔했지만 두지 않은 것들이다. 왜 하나로 충분한지가 기준을 뒤집어 보여준다.

나눌 뻔한 것왜 하나로 충분한가
주차별 history 4개/reports/history가 4주를 배열 하나로 준다. 한 번의 호출이므로 파일도 하나다. 주차를 넘길 때 추가 호출이 없다는 사실까지 파일이 증명한다
W33의 축약 응답api1-weekly-past-W34.json과 스키마가 같다(둘 다 metrics 7필드). 축약형은 대표 하나면 어댑터 검증에 충분하다
certificate·diagnose의 변형파라미터로 응답이 갈리는 것이 관측되지 않았다. 나중에 갈리는 것이 확인되면 규칙 B에 따라 그때 나눈다
승인 실패 응답실패 케이스를 만들려면 일부러 잘못된 요청을 보내야 하는데, 승인 로그가 누적되고 삭제 API가 없어 시도하지 않았다
규칙은 파일 수를 줄이는 쪽이 아니라 재현 가능성과 검증 가능성을 기준으로 세웠다. A·B는 늘리는 규칙이고 C는 줄이는 규칙이며, 셋이 맞물려 일곱이 나왔다.

2.3 어느 파일이 화면 어디에 닿나

7종 중 화면에 값을 그리는 것은 둘이고, 하나는 화면의 특정 상태를 만들며, 나머지 넷은 렌더에 직접 닿지 않는다.

파일크기화면 항목역할
api4-history.json12,114거의 전부
헤더·수준·지표 8칸·서술 4섹션·피드백·생성 표기		화면 재료. 이것만 mock 핸들러가 소비한다
api2-certificate.json3,629지표 · 진행 단계의 분모summary.total_steps. 지금은 상수 10이라 대기 상태
api1-weekly-past-W34.json1,601축약 주차 안내 문구7필드 응답을 재현해 partialMetrics 경로를 검증한다
api5-approve.json387승인 게이트실연동에서 게이트를 여는 신호의 형태
api1-weekly-cached.json5,452—스키마 기준. metrics가 api4 스냅샷과 같은 모양인지 대조
api1-weekly-refresh.json6,104—재분석 시 값과 키가 바뀐다는 사실을 잠가둔다
api3-diagnose.json3,624—등급·확신도가 api4와 어긋나는지 대조
파일 하나가 비면 화면이 통째로 빈다. api4-history.json이 없거나 userId 키가 어긋나면 빈 배열이 돌아와 리포트가 하나도 뜨지 않는다. 나머지 여섯은 없어도 화면은 그려진다 — 대신 스키마가 바뀌었을 때 알아챌 수단이 사라진다.
