mock 데이터 구성안

실호출로 받은 응답만을 재료로 mock을 구성한다. 몇 개 파일로 나눌지, 각 파일에 무엇을 넣을지, 원본 값을 어디까지 손댈지를 근거와 함께 정한다.

작성일 2026-09-03실응답 기반9파일 + 매니페스트

1. 나누는 기준 — 호출 하나가 파일 하나

mock의 재료는 실제로 호출해서 받은 응답뿐이다. 사람이 지어낸 값이나 화면에 맞춰 다듬은 값은 넣지 않는다. 그래야 mock으로 만든 화면이 실연동에서도 같게 동작한다.

형식은 JSON이다

API가 JSON을 준다. 받은 것을 그대로 저장하면 응답과 mock이 1:1로 대응하고, 나중에 실연동으로 바꿀 때 파일을 지우고 fetch로 갈아 끼우면 끝난다.

형식장점이 건에 맞지 않는 이유
JSON응답 원문을 변형 없이 보존한다. 중첩 구조(metrics·diagnosis 블록, top_error_types 배열)가 그대로 남는다—
CSV표로 열어 보기 쉽다중첩을 평탄화해야 한다. top_error_types의 유형·횟수 3쌍과 weak_patterns 배열이 한 칸에 뭉개져 원본 대조가 불가능해진다
TS 리터럴타입 검사가 붙는다손으로 고치기 쉬워 원본이 오염된다. 어디까지가 실응답인지 구분이 사라진다

자르는 기준은 화면이 아니라 호출이다

화면 기준으로 자르면 "이 값이 어느 호출에서 왔는지"를 잃는다. 호출 기준으로 자르면 파일 이름이 곧 재현 명령이 된다.

api4-history.json  ←  curl -X GET "$B/reports/history/$U?limit=30" -H "X-DE-API-KEY: $DE_API_KEY"

2. 몇 개로 나누는가 — 9개 + 매니페스트

호출 5개에 대해 응답 형태가 갈리는 변형을 더해 9개가 된다. API 1은 같은 엔드포인트인데 파라미터에 따라 스키마가 달라져 셋으로 나눴다.

파일호출크기무엇이 들어 있고 왜 필요한가

api1-weekly-refresh.json…&refresh=true6,025재분석본. 캐시본과 21개 필드의 값이 달라진다. 같은 주차라도 호출 시점에 따라 값이 흔들린다는 증거

화면은 api4-history.json 하나만 쓴다. 그런데도 9개를 두는 이유는 나머지가 대조용이기 때문이다 — 필드명이 호출마다 다르고(studentUuid↔student_uuid), 같은 값이 호출마다 어긋나며(확신도 0.8↔0.85), 주차에 따라 필드가 사라진다. 어댑터가 이 셋을 모두 흡수하는지 검증하려면 원본이 남아 있어야 한다.

3. 안에 무엇을 넣는가 — 식별자만 바꾸고 지표는 그대로

원본은 명세서 예시와 같은 29기 정승(100030029410)이다. LMS-FE 데모 로그인 계정과 맞추려고 식별자와 이름만 34기 황수빈으로 바꿨다. 지표는 한 자리도 건드리지 않았다.

그 외 전부—원본 값 그대로
ext-sync-students.json만 예외다. 치환본이 아니라 실제 황수빈 레코드다. /sync/students가 123명 전원을 주므로 황수빈을 그대로 뽑아 쓸 수 있었다. 그래서 이 파일의 과제 10/9/1·퀴즈 7/6/91.0은 실제 LMS 값이다.

뺀 것

markdown_content를 제거했다. 주차당 약 2,900자이고 api4-history.json이 4주치라 그대로 두면 파일이 세 배가 되는데, 화면은 이 필드를 읽지 않는다. 문서 형태가 필요하면 api1-weekly.md가 같은 내용을 담고 있다.

4. 결측을 0으로 채우지 않는다

이 mock에서 가장 중요한 규칙이다. 응답의 0은 "0이다"와 "모른다" 두 가지를 뜻하는데, 구분하지 않고 채우면 화면이 사실이 아닌 것을 사실처럼 보여준다.

값잘못된 해석실제 뜻과 mock에서의 처리
assignments_completed: 0과제를 0건 제출했다미수집이다. 같은 응답의 missing_fields: ["assignments"]가 알려준다. 같은 학생이 /sync/students에서는 9건 제출이다. mock은 missing_fields를 함께 보존해 화면이 구분할 수 있게 한다
attendance_rate: 100.0출석률이 100%다집계가 안 된 값이다. 결석 11일인 학생도 100.0이다. mock에 원본 그대로 두되 매니페스트에 특이사항으로 기록했다
avg_score_pct: 0.0퀴즈 평균이 0점이다미채점이다. 응시가 0이면 이 값이 온다. 점수로 그리면 0점을 받은 것처럼 보인다
W33·W34의 사라진 필드힌트를 한 번도 안 썼다수집 자체가 없다. metrics_snapshot이 7필드로 축약된다. mock은 없는 키를 만들어 넣지 않고 그대로 비운다. 화면은 이 주차를 축약으로 표시한다
top_error_types 3건이게 에러의 전부다상위 3개만 온다. 실측에서 세 건의 합이 total_errors의 62.6%였다. 나머지 37.4%는 어디에도 없고 '기타' 항목도 없다

매니페스트에 남긴 특이사항

_manifest.json의 knownQuirks에 일곱 건을 적어 두었다. mock을 다시 만들거나 실연동으로 바꿀 때 확인해야 할 목록이다.

attendance_rate는 원본이 전원 100.0 (ext-sync의 absent 3일과 불일치)
assignments_completed는 항상 0이고 missing_fields:['assignments'] — 미수집이지 0건 제출이 아님
avg_score_pct 0.0은 미채점이지 0점이 아님
risk.status_label이 status를 반영하지 않음 (completed_waiting인데 '정상 훈련')
weakness 블록은 stalled_risk 외 전부 metrics·diagnosis 복사본
과거 주차(W33·W34)는 metrics 7필드. 결측을 0으로 채우지 말 것
weekly의 language·current_step이 ext-sync의 playlang과 다름
매니페스트에 틀린 줄이 하나 있다. api1-weekly.md의 note가 contributing_signals·action_priority·recommended_action이 여기에만 나온다고 적고 있으나, 실제 파일에는 그 세 항목이 없다. Markdown은 JSON과 같은 내용을 문서로 렌더한 것이고 추가 필드는 없다. 이 줄은 정정이 필요하다.

5. 실연동으로 바꿀 때

파일과 호출이 1:1이라 교체 지점이 분명하다. 지금은 index.ts가 userId로 이력을 찾아 주는데, 이 매핑만 fetch로 바꾸면 나머지 코드는 그대로다.

// 지금
export const DATALAKE_HISTORY = { [DEMO_USER_ID]: history }

// 실연동
GET $B/reports/history/{studentUuid}?limit=30   →  같은 배열
mock 파일대체할 호출주의
api4-history.jsonGET /reports/history/{uuid}?limit=30화면이 쓰는 유일한 호출. 여기만 바꾸면 화면이 산다
api2-certificate.jsonGET /certificate/{uuid}total_steps가 필요하면 함께 호출해야 한다. 지금은 상수 10
나머지 7개—대조·회귀 검증용이라 화면 전환과 무관하다. 스키마가 바뀌면 다시 수집한다
수집 시점을 함께 기록한다. _manifest.json의 collectedAt은 2026-09-02다. 응답이 캐시본이라 시점에 따라 값이 달라지고, 실제로 refresh=true로 다시 부르면 21개 필드가 바뀐다. 언제 받은 값인지 없이는 어긋남을 판단할 수 없다.
2026-09-03 기준 실호출 결과다. 인증 키는 저장소에 두지 않고 환경변수로 참조한다.
