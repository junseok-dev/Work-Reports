mock 데이터 구성안

실호출로 받은 응답만을 재료로 mock을 구성한다. 몇 개 파일로 나눌지, 각 파일에 무엇을 넣을지, 원본 값을 어디까지 손댈지를 근거와 함께 정한다.

작성일 2026-09-03실응답 기반9파일 + 매니페스트

1. 무엇을 담고 무엇을 담지 않나

mock의 재료는 명세서의 다섯 API를 실제로 호출해서 받은 응답뿐이다. 그래야 mock으로 만든 화면이 실연동에서도 같게 동작한다.

값을 지어내지 않는다. 응답이 비어 있거나 필드가 없으면 비어 있는 채로 둔다. 화면이 허전하다고 그럴듯한 숫자를 채우면, 실연동으로 바꾸는 날 화면이 전혀 다른 모습이 되고 그때는 무엇이 달라졌는지 가릴 수 없다.

1.1 형식은 JSON, 자르는 단위는 호출

API가 JSON을 준다. 받은 것을 그대로 저장하면 응답과 mock이 1:1로 대응하고, 실연동으로 바꿀 때 파일을 지우고 fetch로 갈아 끼우면 끝난다. 화면 기준으로 자르면 "이 값이 어느 호출에서 왔는지"를 잃는다.

api4-history.json  ←  curl -X GET "$B/reports/history/$U?limit=5" -H "X-DE-API-KEY: $DE_API_KEY"
형식장점이 건에 맞지 않는 이유
JSON응답 원문을 변형 없이 보존한다. 중첩 구조가 그대로 남는다—
CSV표로 열어 보기 쉽다중첩을 평탄화해야 한다. top_error_types의 유형·횟수 3쌍과 weak_patterns 배열이 한 칸에 뭉개져 원본 대조가 불가능해진다
TS 리터럴타입 검사가 붙는다손으로 고치기 쉬워 원본이 오염된다. 어디까지가 실응답인지 구분이 사라진다

1.2 손댄 것은 식별자와 두 필드뿐

원본은 명세서 예시와 같은 29기 정승(100030029410)이다. LMS-FE 데모 로그인 계정과 맞추려고 식별자와 이름만 34기 황수빈으로 바꿨다. 지표와 서술은 한 자리도 건드리지 않았다.

1.3 결측을 0으로 채우지 않는다

이 mock에서 가장 중요한 규칙이다. 응답의 0은 "0이다"와 "모른다" 두 가지를 뜻하는데, 구분하지 않고 채우면 화면이 사실이 아닌 것을 사실처럼 보여준다.

값잘못된 해석실제 뜻과 mock에서의 처리
assignments_completed: 0과제를 0건 제출했다미수집이다. 같은 응답의 missing_fields: ["assignments"]가 알려준다. mock은 이 선언을 함께 보존해 화면이 구분할 수 있게 한다
attendance_rate: 100.0출석률이 100%다집계가 안 된 값이다. 학생 5명·주차 4개가 전부 같은 값이라 구별력이 없다. 원본 그대로 두되 매니페스트에 특이사항으로 기록했다
avg_retry_gap_min: 0.0재시도까지 0분 걸렸다축약 주차의 결측이다. api1-weekly-past-W34.json에서 관측된다
W33·W34의 사라진 필드힌트를 한 번도 안 썼다수집 자체가 없다. metrics_snapshot이 7필드로 축약된다. mock은 없는 키를 만들어 넣지 않고 그대로 비운다
top_error_types 3건이게 에러의 전부다상위 3개만 온다. 실측에서 세 건의 합이 total_errors의 63.6%였다. 나머지 36.4%는 어디에도 없고 '기타' 항목도 없다

매니페스트에 남긴 특이사항

_manifest.json의 knownQuirks에 열 건을 적어 두었다. mock을 다시 만들거나 실연동으로 바꿀 때 확인해야 할 목록이다.

attendance_rate는 학생 5명·주차 4개·API 3종 전부 100.0 — 구별력이 없어 쓸 수 없음
assignments_completed는 항상 0이고 missing_fields:['assignments'] — 미수집이지 0건 제출이 아님
퀴즈는 5개 API와 명세서 필드 사전 모두에 필드가 없음
risk.status_label이 status를 반영하지 않음 (completed_waiting인데 '정상 훈련')
weakness 블록은 stalled_risk 외 전부 metrics·diagnosis 복사본
과거 주차(W33·W34)는 metrics 7필드. 결측을 0으로 채우지 말 것 (키 자체가 없음)
weekly의 language가 학생을 가리지 않고 python — 값 범위가 명세에 없음
비율·평균은 소수 2자리로 반올림돼 옴. 재계산하면 응답값과 어긋남 (478÷4946=0.0966 → 0.1)
top_error_types는 상위 3종만. W36 기준 합계가 total_errors의 63.6%이고 '기타' 항목이 없음
타임스탬프에 타임존 표기가 없고 log_id만 KST

2. mock 7종 한눈에

폴더에는 파일이 아홉 개지만 mock으로 쓰이는 것은 JSON 7종이다. 나머지 둘은 성격이 다르다 — 하나는 참고 문서, 하나는 기록이다.

갈래개수무엇인가
mock 데이터7종index.ts가 import하는 JSON. 화면과 테스트가 실제로 읽는다
참고 문서1건api1-weekly.md. Markdown이라 import할 수 없다
기록1건_manifest.json. 데이터가 아니라 데이터의 출처다

2.1 무엇을 넣을지 — 세 가지를 다 통과해야 한다

응답이라고 다 넣지 않는다. 셋 중 하나라도 걸리면 mock에 들어가지 않는다.

기준왜 그런가여기서 걸러진 것
1명세서의 다섯 API여야 한다문서에 없는 엔드포인트는 계약이 아니다. 언제 사라져도 이상하지 않은 것에 화면을 의존시킬 수 없다/sync/students — 출결·과제·퀴즈·학습 시간이 여기 있었지만 뺐다
2import할 수 있어야 한다index.ts가 읽어 핸들러에 넘겨야 mock으로 동작한다. 형식이 다르면 화면도 테스트도 못 쓴다api1-weekly.md — 내용은 같지만 Markdown이라 참고 문서로 분류
3실제로 호출해 받은 값이어야 한다지어낸 값을 섞으면 실연동으로 바꾸는 날 무엇이 달라졌는지 가릴 수 없다채워 넣었던 W33·W34의 지표 — 되돌리고 축약된 채로 뒀다

2.2 어떻게 나눌지 — 재현 단위와 스키마

통과한 응답을 파일로 자르는 기준이다. 한 파일이 한 번의 호출로 재현되어야 하고, 어댑터가 다르게 처리해야 하는 응답은 갈라야 한다.

규칙이유적용 결과
A엔드포인트가 다르면 나눈다파일 이름이 곧 재현 명령이 된다. 어느 호출에서 온 값인지 잃지 않는다5개 호출 → 최소 5개 파일
B스키마가 갈리면 또 나눈다키가 달라지면 어댑터가 다르게 처리해야 한다. 둘 다 흡수하는지 확인하려면 원본 두 벌이 필요하다API 1이 ?format=json · &week= · &refresh=true로 세 벌
C값만 다르면 나누지 않는다같은 모양을 여러 벌 두면 어느 것이 기준인지 흐려진다주차별 파일을 따로 두지 않았다
 
API 1  /reports/weekly      → JSON 3종   B에 걸려 셋으로
                                 + Markdown 1건 (기준 2에 걸려 참고 문서)
API 2  /certificate        → 1종
API 3  /analysis/diagnose  → 1종
API 4  /reports/history    → 1종    ← 화면이 쓰는 유일한 파일
API 5  /feedback/approve   → 1종
                             ──────
                             JSON 7종

나누지 않은 것들 — 규칙 C가 걸러낸 경우

나눌 뻔했지만 두지 않은 것들이다. 왜 하나로 충분한지가 기준을 뒤집어 보여준다.

나눌 뻔한 것왜 하나로 충분한가
주차별 history 4개/reports/history가 4주를 배열 하나로 준다. 한 번의 호출이므로 파일도 하나다. 주차를 넘길 때 추가 호출이 없다는 사실까지 파일이 증명한다
W33의 축약 응답api1-weekly-past-W34.json과 스키마가 같다(둘 다 metrics 7필드). 축약형은 대표 하나면 어댑터 검증에 충분하다
certificate·diagnose의 변형파라미터로 응답이 갈리는 것이 관측되지 않았다. 나중에 갈리는 것이 확인되면 규칙 B에 따라 그때 나눈다
승인 실패 응답실패 케이스를 만들려면 일부러 잘못된 요청을 보내야 하는데, 승인 로그가 누적되고 삭제 API가 없어 시도하지 않았다
규칙은 파일 수를 줄이는 쪽이 아니라 재현 가능성과 검증 가능성을 기준으로 세웠다. A·B는 늘리는 규칙이고 C는 줄이는 규칙이며, 셋이 맞물려 일곱이 나왔다.

2.3 어느 파일이 화면 어디에 닿나

7종 중 화면에 값을 그리는 것은 둘이고, 하나는 화면의 특정 상태를 만들며, 나머지 넷은 렌더에 직접 닿지 않는다.
