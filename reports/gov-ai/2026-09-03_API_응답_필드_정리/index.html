GOV-AI DataLake · API Verification

GOV-AI API 응답 필드 정리

명세서의 5개 API를 직접 호출해 응답 필드를 전부 펴고, 출결·과제·퀴즈로 어떤 통계가 가능하고 무엇이 불가능한지를 호출 명령과 응답 값으로 가른다.

작성일 2026-09-03API 실호출 검증GOV-AI DataLake v1.0.0

1. 검증 개요

GOV-AI DataLake 명세서(REPORT-API-CALL.md v1.3)가 정의한 5개 API를 2026-09-03에 직접 호출해 실제 응답을 확인했다. 주간 진단 리포트 화면이 어떤 값을 쓸 수 있고 어떤 값을 쓸 수 없는지를, 호출 명령과 응답 값을 근거로 정리한다.

대상 https://datalake.isitsoft.kr/api/v1 · API v1.0.0 · 인증 헤더 X-DE-API-KEY. 검증 수강생은 명세서 예시와 같은 100030029410(정승, 29기 A반)이며, 화면 구성 예시에는 데모 계정 100051503818(황수빈, 34기)을 쓴다.

이 문서의 구성

호출에서 시작해 필드, 그리고 쓸 수 있는지 판단 순으로 간다.

장다루는 것여기서 답하는 질문
2장다섯 엔드포인트를 어떤 명령으로 불렀고 응답의 최상위 구조가 어떤가어떻게 부르는가 · 무엇이 통째로 오는가 · 문서 밖 /sync/students는 왜 응답하는가
3장응답 필드 전체 사전 — 각 필드의 의미·타입·실측값이 필드가 무슨 뜻인가 · 어떤 값이 왔는가 · 호출마다 이름이 왜 다른가
4장값이 어떤 모양으로 오는가 — 형식·단위·표기이름은 어떻게 오는가 · 시각이 왜 세 형식인가 · 숫자가 반올림돼 있나 · "없다"를 어떻게 구분하나
5장출결·과제·퀴즈 — 어떤 통계가 되고 무엇이 안 되는가필드는 오는데 왜 못 쓰는가 · 그래도 낼 수 있는 통계는 무엇인가 · GOV-AI에 무엇을 요청해야 하는가
화면 항목마다 어떤 값이 들어가 어떤 숫자·문장이 되는지는 이 보고서가 아니라 주간 진단 리포트 항목별 데이터에서 다룬다.

호출 환경

이 문서의 모든 명령은 아래 환경변수를 전제한다. 키는 저장소에 두지 않는다.

export DE_API_KEY="<명세서 1.1의 X-DE-API-KEY>"
export B="https://datalake.isitsoft.kr/api/v1"
export U="100030029410"
export PYTHONIOENCODING=utf-8

응답을 읽을 때는 PYTHONIOENCODING=utf-8과 --no-ensure-ascii가 둘 다 있어야 한글이 보인다. 앞이 없으면 콘솔 코드페이지에서 깨지고, 뒤가 없으면 \uc815\uc2b9 형태로 이스케이프된다.

curl -sS "$B/reports/weekly/$U?format=json" -H "X-DE-API-KEY: $DE_API_KEY" \
  | python -m json.tool --no-ensure-ascii
Windows 주의 Git Bash·PowerShell 모두 curl.exe에 명령행 인자를 넘길 때 한글을 시스템 코드페이지(CP949)로 변환한다. 한글이 든 요청 본문을 -d로 인라인 전달하면 서버가 UTF-8로 디코딩하지 못해 400 There was an error parsing the body가 난다. 본문은 파일로 저장해 --data-binary @file로 보내야 한다. macOS·Linux에서는 명세서 예시가 그대로 동작한다.

2. API 1~5 호출과 응답

명세서 §2의 다섯 엔드포인트를 순서대로 호출한 결과다. 각 호출의 실제 명령과 응답의 최상위 구조를 기록한다. 필드 하나하나는 3장에서 편다.

API 1. 주간 AI 학습 맞춤 진단 리포트

curl -X GET "$B/reports/weekly/$U?format=json" -H "X-DE-API-KEY: $DE_API_KEY"

최상위 10개 블록이 온다.

studentUuid · year_week · week_no · week_label · week_range · cached
metrics · diagnosis · weakness · risk

metrics는 24필드다. 이 목록이 진단 리포트가 쓸 수 있는 지표의 전부다.

studentUuid  userId  name  cohortId  cohort  group  language
steps_completed  current_step  stalled_days_on_current_step  days_since_last_activity
active_days_count  total_runs  total_errors  error_per_run
hint_requests_count  hint_per_active_day  avg_retry_gap_min  max_retry_gap_min
top_error_types  assignments_completed  attendance_rate  data_freshness  missing_fields

API 2. LMS 연동용 역량 증명서

curl -X GET "$B/certificate/$U" -H "X-DE-API-KEY: $DE_API_KEY"
version · issue_timestamp · student · summary · technical_proof
project_and_portfolio · ai_analysis_narrative · human_in_the_loop

project_and_portfolio 블록은 API 1과 필드명이 다르다.

"project_and_portfolio": {
  "completed_assignments": 0,      // API 1은 assignments_completed
  "attendance_rate": 100.0,
  "collaboration_score": 85.0
}

summary.total_steps = 10은 이 API에만 있어, 진행률을 10/10으로 표시하려면 여기서 가져오거나 상수로 두어야 한다.

API 3. 온디맨드 수준 진단

curl -X POST "$B/analysis/diagnose/$U" -H "X-DE-API-KEY: $DE_API_KEY"

최상위 10필드가 평탄하게 온다. API 1의 diagnosis 블록과 같은 구성이다.

studentUuid · grade · confidence · grade_rationale · weak_patterns · risk_flags
recommendations_for_instructor · suggested_feedback_draft · analyzed_at · model_meta
지표가 아예 없다. total_runs·error_per_run 같은 정량 값이 오지 않는다. 진단 텍스트만 반환하는 엔드포인트다.

API 4. 주차별 리포트 이력

curl -X GET "$B/reports/history/$U?limit=5" -H "X-DE-API-KEY: $DE_API_KEY"

배열로 오며 항목당 20필드다. API 1과 필드명이 다르다.

API 1 (weekly)API 4 (history)
studentUuidstudent_uuid
diagnosis.recommendations_for_instructorrecommendations
diagnosis.suggested_feedback_draftfeedback_draft
risk.statusrisk_status
diagnosis.model_meta.provider · .modelllm_provider · llm_model
4개 블록 중첩전부 평탄화 + metrics_snapshot · markdown_content

주차별 metrics_snapshot을 열면 주차마다 필드 수가 다르다.

2026-W33  metrics_snapshot   7개 필드
2026-W34  metrics_snapshot   7개 필드
2026-W35  metrics_snapshot  24개 필드
2026-W36  metrics_snapshot  24개 필드

과거 두 주차는 steps_completed · current_step · total_runs · total_errors · error_per_run · active_days_count · attendance_rate 7개로 축약된다. 힌트·재시도·정체·에러 유형과 신원 필드가 사라진다.

API 5. 강사 피드백 승인

cat > payload.json <<'EOF'
{
  "studentUuid": "100030029410",
  "approved_by": "[TEST] 필드 확인",
  "feedback_text": "[TEST] API 5 응답 필드 확인용",
  "status": "APPROVED"
}
EOF

curl -X POST "$B/feedback/approve" -H "X-DE-API-KEY: $DE_API_KEY"   -H "Content-Type: application/json" --data-binary @payload.json
{"status": "SUCCESS", "log_id": "fb_20260903103059_100030029410", "approved_by": "[TEST] 필드 확인"}

응답은 3필드뿐이다. 승인 로그가 누적 생성되고 삭제 API가 없으므로, 검증 호출에는 [TEST] 표기를 붙여 나중에 골라낼 수 있게 했다.

log_id의 시각 103059는 KST다. 같은 순간 다른 응답의 analyzed_at·data_freshness·issue_timestamp는 UTC로 온다. 한 서비스 안에서 타임존이 섞여 있다.

문서 밖 엔드포인트 — /sync/students

명세서 5개 API에는 없고 /openapi.json에서 찾은 엔드포인트다.

curl -X GET "$B/sync/students?limit=200" -H "X-DE-API-KEY: $DE_API_KEY"
student_uuid · user_id · name · cohort_id · cohort_label · education_title · training_status
assignments {total, submitted, not_submitted}
quizzes     {total, attempted, avg_score_pct}
attendance  {present, late, early_leave, absent, excused}
atmux       {total_duration_sec, total_duration_hours, weekly_daily_avg_hours, avg_cpu_util, telemetry_count}
playlang    {current_step, course, language, total_events, runs_count, errors_count, hints_count, error_rate_pct}
last_synced_at

학생 마스터라 123명 전원이 오고, 주차 개념이 없다. last_synced_at 시점의 누적 현재값이다. 이 블록들의 실측값과 그것으로 무엇을 낼 수 있는지는 4장에서 다룬다.

왜 호출되는가

문서에 없는데 응답이 오는 이유는 인증이 하나이기 때문이다. 5개 API와 같은 X-DE-API-KEY를 쓰고 엔드포인트별 권한 구분이 없다. 문서에 안 적혔을 뿐 막혀 있지 않다.

그렇다면 이 엔드포인트는 무엇을 위한 것인가. 응답에서 관측되는 것은 다음과 같다.

관측무엇을 말해주나
이름이 sync다분석(analysis)·진단(diagnose)·리포트(reports)와 이름 계열이 다르다.
last_synced_at을 담는다주차가 아니라 마지막 동기화 시각을 기준으로 한다. 분석 산출물이라면 필요 없는 필드다.
주차 개념이 없다123명 전원의 현재 누적값만 온다. 주차를 바꿔 호출할 수단이 없다.
필드 모양이 LMS와 같다LMS data-ingest-api가 주는 구조를 거의 그대로 따르고 camelCase → snake_case만 바뀌었다.
education_title·training_status가 있다분석에 쓰이지 않는 행정 정보다. 5개 API 어디에도 없다.

종합하면 이 엔드포인트는 분석 결과를 내주는 곳이 아니라 LMS가 넘긴 원천이 제대로 적재됐는지 확인하는 동기화 점검용으로 보인다. LMS가 보낸 값이 그대로 남아 있는 것이지, GOV-AI가 분석해 만든 값이 아니다. 적재 경로는 4.5에 정리했다.

다만 이는 관측에 근거한 해석이다. 명세서에 설명이 없어 확정할 수 없으므로, 이 엔드포인트를 우리가 계속 호출해도 되는지와 값의 갱신 주기를 GOV-AI에 확인해야 한다(4장 요청 항목).

주차가 없어 주간 리포트의 시계열에는 그대로 넣을 수 없다. 무엇을 쓸 수 있고 무엇을 못 쓰는지는 4장에서 가른다.

3. 응답 필드 사전

2장의 호출이 돌려준 필드를 전부 편다. 각 필드가 무엇인지, 어떤 값이 왔는지, 진단 리포트가 쓰는지를 함께 적는다. 표의 출처는 아래 호출을 가리킨다.

같은 값이 세 곳에등급·확신도·근거·약점·피드백 초안은 API 1·3·4 모두에 있다. API 1의 diagnosis 블록은 API 3의 최상위와 키가 100% 일치한다. 어느 쪽을 원본으로 볼지 정해두지 않으면 값이 갈렸을 때 판단할 근거가 없다.
같은 뜻, 다른 이름studentUuid↔student_uuid, suggested_feedback_draft↔feedback_draft, recommendations_for_instructor↔recommendations, assignments_completed↔completed_assignments. 표기법(camel/snake)과 어순이 API마다 다르다.
같은 이름, 다른 모양model_meta가 API 1·2는 5키, API 3은 3키다. prompt_version은 API 3에만, cached·week_label은 API 1·2에만 있다.
확신도가 어긋난다같은 학생·같은 시점인데 API 1은 0.8, API 3은 0.85다. API 3은 POST로 호출할 때마다 새로 분석하므로 캐시본인 API 1과 값이 벌어진다.
총 단계 수는 API 2에만total_steps는 API 2의 summary에만 있다. 화면이 쓰는 API 4에는 없어 FE가 상수 10을 들고 있다.
고정값이 섞여 있다attendance_rate 100.0, collaboration_score 85.0, error_resolution_rate 0.95, human_in_the_loop.status APPROVED는 학생과 주차를 바꿔도 움직이지 않았다. 필드가 온다는 것과 값이 쓸 만하다는 것은 별개다.

4. 값의 형태와 해석

3장이 어떤 필드가 오는가였다면 여기는 그 값이 어떤 모양으로 오는가다. 같은 뜻이라도 형식에 따라 읽는 법이 달라지고, 잘못 읽으면 화면에 틀린 값이 뜬다. 모든 예시는 데모 계정 황수빈(100051503818)의 실응답이다.

4.1 사람을 가리키는 값

4.6 숫자는 이미 반올림돼 온다

비율과 평균은 서버가 소수 두 자리로 반올림해 보낸다. 원본 나눗셈과 값이 다르다.

W34       0.22    31 ÷ 140 = 0.22143    0.22   일치
W35       0.1     27 ÷ 264 = 0.10227    0.10   일치
W36       0.1    478 ÷ 4946 = 0.09664   0.10   일치

W36의 0.1은 0.10의 뒤 0을 JSON이 떨어뜨린 것이지 소수 한 자리가 아니다. 그리고 원본은 0.0966이므로, 우리가 total_errors ÷ total_runs로 다시 계산하면 응답값과 어긋난다. 화면에는 응답값을 그대로 쓴다.

5.2 "온다"와 "쓸 수 있다"는 다르다

말이 엇갈린 이유는 막히는 지점이 항목마다 다르기 때문이다. 네 가지를 구분하지 않으면 같은 항목을 두고 "온다"와 "없다"가 둘 다 맞는 말이 된다.

막히는 지점해당 항목무슨 뜻인가
1부르는 곳이 다르다퀴즈명세서는 5개 API만 다루는데 실제 서버의 /openapi.json에는 24개가 있다. "퀴즈가 왔다"는 /sync/students를, "퀴즈가 없다"는 5개 API를 가리킨 말이라 둘 다 참이었다.
2필드는 있는데 값이 틀렸다출결attendance_rate가 학생과 무관하게 전부 100.0이다. missing_fields에 attendance가 없으므로 서버는 받았다고 본다. 결측이 아니라 틀린 값이라 더 위험하다.
3서버가 미수집을 선언한다과제missing_fields: ["assignments"]. 여기서 0은 0건 제출이 아니라 안 받음이다. 서버가 스스로 알려주는 정직한 처리이므로, 이 선언을 보면 오해하지 않는다.
4주차로 나눌 수 없다셋 다/sync/students는 last_synced_at 시점의 누적 현재값이다. 주차 파라미터가 없어 "이번 주"나 "지난주 대비"를 만들 수 없다.

5.6 화면 설계상으로는 이미 갈라져 있다

LMS-DOCS/30_설계/60_기능/기능_명세/P0_12_수강생_과정별_역량_리포트.md가 원천을 나눠 놓았다.

P0-STU-DIAG-004 완료 기준 — "지표는 퀴즈·과제 점수가 아니라 실습 행동 로그(정체·에러율·힌트 의존·재시도 간격) 기반임"

같은 문서가 구 competency 화면과의 차이를 데이터 원천으로 구분한다 — 구 화면은 "퀴즈·과제·출결·기록 집계", 진단 리포트는 "실습 단계 진행·에러·힌트·재시도 지표"다. 실제 API 응답이 이 구분과 일치한다. 출결·과제·퀴즈는 교육과정 허브의 출결/태도·과제·퀴즈 전용 탭이 담당한다. 진단 리포트에 넣는다면 그 탭들과 같은 원천(/sync/students 또는 LMS 직접 조회)을 써야 값이 어긋나지 않는다.
