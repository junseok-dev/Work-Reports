GOV-AI DataLake · API Verification

GOV-AI API 응답 필드 정리

명세서의 5개 API를 직접 호출해 응답 필드를 전부 펴고, 출결·과제·퀴즈로 어떤 통계가 가능하고 무엇이 불가능한지를 호출 명령과 응답 값으로 가른다.

작성일 2026-09-03API 실호출 검증GOV-AI DataLake v1.0.0

1. 검증 개요

GOV-AI DataLake 명세서(REPORT-API-CALL.md v1.3)가 정의한 5개 API를 2026-09-03에 직접 호출해 실제 응답을 확인했다. 이 문서는 명세서의 다섯 엔드포인트만 다룬다 — 문서에 없는 엔드포인트는 계약 밖이라 언제 바뀌어도 이상하지 않으므로 근거로 쓰지 않는다. 주간 진단 리포트 화면이 어떤 값을 쓸 수 있고 어떤 값을 쓸 수 없는지를, 호출 명령과 응답 값을 근거로 정리한다.

대상 https://datalake.isitsoft.kr/api/v1 · API v1.0.0 · 인증 헤더 X-DE-API-KEY. 검증 수강생은 명세서 예시와 같은 100030029410(정승, 29기)이며, 화면 구성 예시에는 데모 계정 100051503818(황수빈, 34기)을 쓴다.

이 문서의 구성

호출에서 시작해 필드, 그리고 쓸 수 있는지 판단 순으로 간다.

장다루는 것여기서 답하는 질문
2장다섯 엔드포인트를 어떤 명령으로 불렀고 응답의 최상위 구조가 어떤가어떻게 부르는가 · 무엇이 통째로 오는가 · 응답의 최상위가 어떻게 생겼나
3장응답 필드 전체 사전 — 각 필드의 의미·타입·실측값이 필드가 무슨 뜻인가 · 어떤 값이 왔는가 · 호출마다 이름이 왜 다른가
4장값이 어떤 모양으로 오는가 — 형식·단위·표기이름은 어떻게 오는가 · 시각이 왜 세 형식인가 · 숫자가 반올림돼 있나 · "없다"를 어떻게 구분하나
5장출결·과제·퀴즈 — 어떤 통계가 되고 무엇이 안 되는가필드는 오는데 왜 못 쓰는가 · 그래도 낼 수 있는 통계는 무엇인가 · GOV-AI에 무엇을 요청해야 하는가
화면 항목마다 어떤 값이 들어가 어떤 숫자·문장이 되는지는 이 보고서가 아니라 주간 진단 리포트 항목별 데이터에서 다룬다.

호출 환경

이 문서의 모든 명령은 아래 환경변수를 전제한다. 키는 저장소에 두지 않는다.

export DE_API_KEY="<명세서 1.1의 X-DE-API-KEY>"
export B="https://datalake.isitsoft.kr/api/v1"
export U="100030029410"
export PYTHONIOENCODING=utf-8

응답을 읽을 때는 PYTHONIOENCODING=utf-8과 --no-ensure-ascii가 둘 다 있어야 한글이 보인다. 앞이 없으면 콘솔 코드페이지에서 깨지고, 뒤가 없으면 \uc815\uc2b9 형태로 이스케이프된다.

curl -sS "$B/reports/weekly/$U?format=json" -H "X-DE-API-KEY: $DE_API_KEY" \
  | python -m json.tool --no-ensure-ascii
Windows 주의 Git Bash·PowerShell 모두 curl.exe에 명령행 인자를 넘길 때 한글을 시스템 코드페이지(CP949)로 변환한다. 한글이 든 요청 본문을 -d로 인라인 전달하면 서버가 UTF-8로 디코딩하지 못해 400 There was an error parsing the body가 난다. 본문은 파일로 저장해 --data-binary @file로 보내야 한다. macOS·Linux에서는 명세서 예시가 그대로 동작한다.

2. API 1~5 호출과 응답

명세서 §2의 다섯 엔드포인트를 순서대로 호출한 결과다. 각 호출의 실제 명령과 응답의 최상위 구조를 기록한다. 명세서에 정의된 다섯 개가 전부다. 필드 하나하나는 3장에서 편다.

API 1. 주간 AI 학습 맞춤 진단 리포트

curl -X GET "$B/reports/weekly/$U?format=json" -H "X-DE-API-KEY: $DE_API_KEY"

최상위 10개 블록이 온다.

studentUuid · year_week · week_no · week_label · week_range · cached
metrics · diagnosis · weakness · risk

metrics는 24필드다. 이 목록이 진단 리포트가 쓸 수 있는 지표의 전부다.

studentUuid  userId  name  cohortId  cohort  group  language
steps_completed  current_step  stalled_days_on_current_step  days_since_last_activity
active_days_count  total_runs  total_errors  error_per_run
hint_requests_count  hint_per_active_day  avg_retry_gap_min  max_retry_gap_min
top_error_types  assignments_completed  attendance_rate  data_freshness  missing_fields

API 2. LMS 연동용 역량 증명서

curl -X GET "$B/certificate/$U" -H "X-DE-API-KEY: $DE_API_KEY"
version · issue_timestamp · student · summary · technical_proof
project_and_portfolio · ai_analysis_narrative · human_in_the_loop

project_and_portfolio 블록은 API 1과 필드명이 다르다.

"project_and_portfolio": {
  "completed_assignments": 0,      // API 1은 assignments_completed
  "attendance_rate": 100.0,
  "collaboration_score": 85.0
}

summary.total_steps = 10은 이 API에만 있어, 진행률을 10/10으로 표시하려면 여기서 가져오거나 상수로 두어야 한다.

API 3. 온디맨드 수준 진단

curl -X POST "$B/analysis/diagnose/$U" -H "X-DE-API-KEY: $DE_API_KEY"

최상위 10필드가 평탄하게 온다. API 1의 diagnosis 블록과 같은 구성이다.

studentUuid · grade · confidence · grade_rationale · weak_patterns · risk_flags
recommendations_for_instructor · suggested_feedback_draft · analyzed_at · model_meta
지표가 아예 없다. total_runs·error_per_run 같은 정량 값이 오지 않는다. 진단 텍스트만 반환하는 엔드포인트다.

API 4. 주차별 리포트 이력

curl -X GET "$B/reports/history/$U?limit=5" -H "X-DE-API-KEY: $DE_API_KEY"

배열로 오며 항목당 20필드다. API 1과 필드명이 다르다.

API 1 (weekly)API 4 (history)
studentUuidstudent_uuid
diagnosis.recommendations_for_instructorrecommendations
diagnosis.suggested_feedback_draftfeedback_draft
risk.statusrisk_status
diagnosis.model_meta.provider · .modelllm_provider · llm_model
4개 블록 중첩전부 평탄화 + metrics_snapshot · markdown_content

주차별 metrics_snapshot을 열면 주차마다 필드 수가 다르다.

2026-W33  metrics_snapshot   7개 필드
2026-W34  metrics_snapshot   7개 필드
2026-W35  metrics_snapshot  24개 필드
2026-W36  metrics_snapshot  24개 필드

과거 두 주차는 steps_completed · current_step · total_runs · total_errors · error_per_run · active_days_count · attendance_rate 7개로 축약된다. 힌트·재시도·정체·에러 유형과 신원 필드가 사라진다.

API 5. 강사 피드백 승인

cat > payload.json <<'EOF'
{
  "studentUuid": "100030029410",
  "approved_by": "[TEST] 필드 확인",
  "feedback_text": "[TEST] API 5 응답 필드 확인용",
  "status": "APPROVED"
}
EOF

curl -X POST "$B/feedback/approve" -H "X-DE-API-KEY: $DE_API_KEY"   -H "Content-Type: application/json" --data-binary @payload.json
{"status": "SUCCESS", "log_id": "fb_20260903103059_100030029410", "approved_by": "[TEST] 필드 확인"}

응답은 3필드뿐이다. 승인 로그가 누적 생성되고 삭제 API가 없으므로, 검증 호출에는 [TEST] 표기를 붙여 나중에 골라낼 수 있게 했다.

log_id의 시각 103059는 KST다. 같은 순간 다른 응답의 analyzed_at·data_freshness·issue_timestamp는 UTC로 온다. 한 서비스 안에서 타임존이 섞여 있다.

3. 응답 필드 사전

2장의 다섯 호출이 돌려준 필드를 전부 편다. 각 필드가 무엇인지, 어떤 값이 왔는지, 진단 리포트가 쓰는지를 함께 적는다. 표의 출처는 아래 호출을 가리킨다.

출처호출무엇을 부른 것인가

쓰임 열은 수강생 주간 진단 리포트와의 관계를 셋으로 나눈다. ● 화면에 값이 나온다 · ◑ 화면에 나오지는 않지만 필요하다 — 호출 식별자이거나, 지금은 상수·파생으로 대체 중이다 · · 지금은 쓰지 않는다. ◑가 붙은 이유는 표 아래 「화면이 읽지 않아도 필요한 값」에 적었다. 어느 필드가 화면의 어느 항목이 되는지는 항목별 데이터 보고서에서 다룬다.

4. 값의 형태와 해석

3장이 어떤 필드가 오는가였다면 여기는 그 값이 어떤 모양으로 오는가다. 같은 뜻이라도 형식에 따라 읽는 법이 달라지고, 잘못 읽으면 화면에 틀린 값이 뜬다. 모든 예시는 데모 계정 황수빈(100051503818)의 실응답이다.

4.1 사람을 가리키는 값

필드실제 값형식이렇게 읽는다
name황수빈문자열 3자수강생 이름이 그대로 온다. 성과 이름이 분리돼 있지 않고 공백도 없다. LMS에 입력된 원문이 그대로 넘어온 것이라, 외국인 수강생이면 로마자나 다른 길이로 올 수 있다. 화면에 그대로 쓰되 성·이름을 잘라 쓰지 않는다
studentUuid"100051503818"문자열 12자숫자처럼 보이지만 문자열이다. 따옴표가 붙어 있다. 학번은 연산 대상이 아니고 앞자리에 0이 올 수 있어서다. 숫자로 바꿔 다루면 앞의 0이 사라지거나 자릿수가 어긋난다
userIdf074a93b-5ad7-…UUID 36자소문자 16진수에 하이픈이 8-4-4-4-12로 들어간다. LMS user.id와 같은 값이라 대소문자를 바꾸거나 하이픈을 빼면 매칭이 깨진다
cohort34기문자열 3자숫자에 한글 접미사가 붙은 표시명이다. 기수 번호가 따로 오지 않으므로 정렬하려면 파싱해야 한다. 문자열로 정렬하면 34기가 9기보다 앞에 온다
cohortIdf34c88f3-7cd2-…UUID 36자기수의 기계용 식별자. 정렬·비교는 이쪽을 쓴다
languagepython소문자 문자열이 값은 확인이 필요하다. 주간 리포트가 학생을 가리지 않고 python을 준다. 값 범위가 명세에 없어 실제 실습 언어를 반영한 것인지 알 수 없다

4.2 주차를 가리키는 값 — 네 가지가 한꺼번에 온다

같은 주차를 네 형식으로 준다. 쓰임이 달라서다.

필드실제 값형식쓰임
year_week2026-W36ISO 8601 주 표기연도가 붙은 고유 키. 해를 넘겨도 겹치지 않는다
week_no36정수정렬용. 화면이 주차를 오름차순으로 놓을 때 쓴다
week_label2026-W36 [08/31~09/06]사람용 문자열그대로 찍으면 되는 표시 문자열
week_range08/31~09/06MM/DD~MM/DD기간만. 연도가 없다 — 12/29~01/04 같은 주차는 어느 해인지 이 값만으로 알 수 없다
ISO 주차는 기수 주차가 아니다. week_no 36은 그 해의 36번째 주라는 뜻이지 수강 36주차가 아니다. 화면의 "14주차"는 기수 시작일에서 우리가 계산한 값이다. 두 숫자를 섞으면 안 된다.

어떤 필드는 기계용 코드로, 어떤 필드는 사람이 읽는 한글로 온다. 규칙이 하나가 아니다.

필드실제 값해석
grade해결사한글 표시명이 그대로 온다. SOLVER 같은 코드값이 아니다. 화면에 바로 쓸 수 있지만, 등급 순서(입문·초급·중급·해결사)를 응답으로는 알 수 없어 코드에 순서를 박아둬야 한다
risk_statuscompleted_waiting이쪽은 snake_case 코드값이다. 화면에 그대로 쓸 수 없어 우리가 한글을 붙인다
status_label정상 훈련같은 응답의 status와 맞지 않는다. completed_waiting(완료 대기)인데 라벨은 정상 훈련이다. 라벨을 믿지 말고 코드값으로 판단해야 한다
human_in_the_loop.statusAPPROVED여기는 대문자다. 세 번째 표기 방식

4.6 숫자는 이미 반올림돼 온다

비율과 평균은 서버가 소수 두 자리로 반올림해 보낸다. 원본 나눗셈과 값이 다르다.

주차       응답값   원본 나눗셈        2자리 반올림
W33       0.45    36 ÷ 80  = 0.45000    0.45   일치
W34       0.22    31 ÷ 140 = 0.22143    0.22   일치
W35       0.1     27 ÷ 264 = 0.10227    0.10   일치
W36       0.1    478 ÷ 4946 = 0.09664   0.10   일치

W36의 0.1은 0.10의 뒤 0을 JSON이 떨어뜨린 것이지 소수 한 자리가 아니다. 그리고 원본은 0.0966이므로, 우리가 total_errors ÷ total_runs로 다시 계산하면 응답값과 어긋난다. 화면에는 응답값을 그대로 쓴다.

구분예형식
건수·일수4946 · 478 · 10정수(int)로 온다
비율·평균·시간0.1 · 40.86 · 0.2실수(float). 소수 두 자리 반올림
정수인데 실수23.0 · 100.0 · 5.0max_retry_gap_min·attendance_rate·risk_score는 값이 딱 떨어져도 .0이 붙어 온다. 타입이 실수로 고정돼 있다는 뜻이다

4.7 에러 유형은 긴 문자열 하나로 온다

형식은 [언어] 정규화된예외경로: 메시지다. 셋 다 같은 틀인데 길이가 제각각이다.

66자  [PYTHON] requests.exceptions.ConnectionError: Max retries exceeded
40자  [PYTHON] asyncio.exceptions.TimeoutError                        ← 메시지 없음
86자  [PYTHON] sqlalchemy.exc.IntegrityError: duplicate key value violates unique constraint
부분해석
[PYTHON]언어 접두사. 대괄호 안 대문자. 실습 언어가 여럿이면 다른 값이 올 것으로 보이나 관측된 것은 이것뿐이다
sqlalchemy.exc.IntegrityError정규화된 예외 경로. 마지막 마디가 예외 클래스명이라 여기만 남기면 IntegrityError가 된다
: duplicate key …있을 때도 없을 때도 있다. TimeoutError에는 메시지가 없다. 콜론으로 자를 때 뒷부분이 비어 있을 수 있다
그대로 쓰면 화면에 안 들어간다. 셋을 이으면 200자가 넘는다. 화면은 접두사·모듈 경로·메시지를 떼고 예외 클래스명만 남긴다 — ConnectionError×105, TimeoutError×104, IntegrityError×95. 원본 값은 건드리지 않고 표시할 때만 줄인다.

4.8 "없다"가 세 가지 방식으로 표현된다

방식예어떻게 다뤄야 하나
키가 아예 없다축약 주차의 top_error_typesW33·W34의 metrics_snapshot은 7필드다(W36은 24필드). null이 아니라 키 자체가 없다. null 검사로는 못 걸러내고 키 존재 여부를 봐야 한다
빈 배열missing_fields: []결측 항목이 없다는 뜻. 반대로 ["assignments"]면 그 항목을 못 받았다는 서버의 선언이다
0이 들어온다avg_score_pct: 0.0
assignments_completed: 0		가장 위험한 형태. 값이 0인지 모르는 것인지 구분되지 않는다. 퀴즈 평균 0.0은 미채점이고, 과제 0은 미수집이다 — 둘 다 0점·0건이 아니다

5. 출결·과제·퀴즈 — 5개 API 안에서는 어떻게 오나

검토 내내 이 셋을 두고 "온다"와 "없다"가 뒤집혔다. 명세서의 다섯 API만 놓고 보면 답이 단순하다 — 필드는 오는데 쓸 수 있는 값이 아니고, 퀴즈는 필드조차 없다. 셋 다 주간 진단 리포트에 넣을 수 없으며, 막히는 지점이 서로 다르다.

5.2 막히는 지점이 셋 다 다르다

"호출하면 값이 온다"와 "그 값을 쓸 수 있다"는 다르다. 어디서 막히는지가 항목마다 달라 말이 계속 엇갈렸다.

막히는 지점해당무슨 뜻인가
1값에 정보가 없다출결attendance_rate가 학생을 바꿔도 주차를 바꿔도 100.0이다. 값이 하나뿐이면 지표로서 구별력이 0이다. 게다가 missing_fields에 attendance가 없으므로 서버는 이 데이터를 받았다고 본다 — 결측으로 처리되지도 않는다
2서버가 미수집을 선언한다과제missing_fields: ["assignments"]. 여기서 0은 0건 제출이 아니라 안 받음이다. 서버가 스스로 알려주므로 오해할 여지는 없지만, 값이 없다는 사실은 그대로다
3필드가 아예 없다퀴즈다섯 응답 어디에도 quiz를 포함하는 키가 없다. 명세서 §4 필드 사전에도 없다. 있다·없다를 논할 것도 없이 계약에 들어 있지 않다

5.3 근거

출결 — 학생과 주차를 바꿔도 값이 하나다

API 1을 학생 다섯 명에게, API 4를 네 주차에 걸쳐 호출한 결과다.

API 1  학생 5명(정승·박상희·장규원·윤승혁·정예린)   attendance_rate  전원 100.0
API 4  정승 W33·W34·W35·W36                        attendance_rate  4주 전부 100.0
API 2  정승                                        attendance_rate  100.0

세 호출·다섯 학생·네 주차에서 관측된 값이 100.0 하나뿐이다. 실제 출결이 전원 만점일 가능성은 없으므로 집계가 동작하지 않는 것으로 본다. 다만 다섯 API 안에는 이를 대조할 수단이 없다 — 결석·지각 일수를 주는 필드가 없기 때문이다.

과제 — 응답이 스스로 미수집을 밝힌다

curl -X GET "$B/reports/weekly/$U?format=json" -H "X-DE-API-KEY: $DE_API_KEY"
  → metrics.assignments_completed : 0
     metrics.missing_fields       : ["assignments"]

같은 응답 안에 값과 그 값이 유효하지 않다는 표시가 함께 온다. 0을 제출 건수로 읽으면 제출한 학생을 미제출로 표시하게 된다. 이 선언이 있는 한 0은 쓸 수 없다.

퀴즈 — 24필드 전수에 없다

API 1의 metrics 24필드, API 2의 31필드, API 3의 12필드, API 4의 44필드, API 5의 7필드를 전수 확인했다. quiz를 포함하는 키가 하나도 없다.

5.4 결론

항목판정이유무엇이 있어야 되나
출결못 한다값에 구별력이 없다attendance_rate가 학생·주차별로 실제 값을 반영하거나, 출석·지각·결석 일수가 주차별로 와야 한다
과제못 한다서버가 미수집 선언missing_fields에서 assignments가 빠지고 assignments_completed에 실제 건수가 들어와야 한다
퀴즈못 한다필드 자체가 없다/reports/weekly·/reports/history에 퀴즈 필드가 신설돼야 한다
셋 다 우리가 풀 수 있는 문제가 아니다. 계산으로 우회하거나 다른 값으로 대체할 방법이 다섯 API 안에 없다. 화면에 넣으려면 GOV-AI가 응답을 고쳐야 하고, 그때까지는 진단 리포트에서 뺀다. 출결·과제·퀴즈는 교육과정 허브의 전용 탭이 LMS에서 직접 가져와 담당한다.

5.5 화면 설계상으로는 이미 갈라져 있다

LMS-DOCS/30_설계/60_기능/기능_명세/P0_12_수강생_과정별_역량_리포트.md가 원천을 나눠 놓았다.

같은 문서가 구 competency 화면과의 차이를 데이터 원천으로 구분한다 — 구 화면은 "퀴즈·과제·출결·기록 집계", 진단 리포트는 "실습 단계 진행·에러·힌트·재시도 지표"다. 실제 API 응답이 이 구분과 정확히 일치한다. 다섯 API가 주는 쓸 만한 값은 전부 실습 행동 로그이고, 출결·과제·퀴즈는 오지 않거나 값이 비어 있다. 설계가 먼저 갈라놓은 선을 데이터가 그대로 따르고 있는 셈이다.
